## Important

2. **README Documents section has a broken link**: `[docs/EVAL_RESULTS.md](prototype/EVAL_RESULTS.md)` — the link text says `docs/EVAL_RESULTS.md` but the href points to `prototype/EVAL_RESULTS.md`. The README's own "Current numbers" table also references `[prototype/EVAL_RESULTS.md](prototype/EVAL_RESULTS.md)`, so the Documents entry is inconsistent with both its own label and the earlier reference. Either the label or the href is wrong.

3. **TestCorpusVendorNeutrality hardcodes an absolute path fallback**: `os.environ.get("GUARDIAN_CORPUS", "/opt/data/projects/custody-guardian/corpus")`. If the env var is not set, the tests will silently run against a machine-specific path that likely doesn't exist on other developers' machines or CI. This will cause `os.listdir` to raise `FileNotFoundError` rather than skipping or using the repo-relative `CORPUS_DIR` already defined at the top of the file. The test class should default to the repo-relative `CORPUS_DIR` (or derive it the same way) instead of a hardcoded absolute path.

4. **LICENSES.md overclaims legal certainty on River/vendor handling**: The sentence "Third-party sources used under facts-only, reference-only terms (e.g. River Learn, vendor documentation, which carry no open license) are cited but not reproduced beyond short attributed references" asserts a legal conclusion ("facts-only, reference-only terms") that is not established by the documents. River's terms of service do not grant a "facts-only" license; facts themselves are not copyrightable, but the *expression* of those facts (the specific wording, structure, selection) is. The corpus provenance table shows entries like "What is a seed phrase?" with sections drawn from River ("Opening definition and Importance section", "WARNING callout from River", etc.) and the source_url pointing to `https://river.com/learn/what-is-a-seed-phrase/`. If these are verbatim excerpts (as the corpus-field rule requires), they are reproductions of River's copyrighted expression, not merely facts. The claim that they are "not reproduced beyond short attributed references" is contradicted by the provenance table showing multiple section-level extractions per entry. The wholesale CC BY-SA license cannot cure this for non-CC sources — you cannot relicense River's text under CC BY-SA just by declaring it.

5. **Provenance table contradicts LICENSES.md on River**: LICENSES.md says River content is "cited but not reproduced beyond short attributed references." The provenance table shows entries like "What is a seed phrase?" (`what-is-a-seed-phrase`) with 10+ River-derived sections listed as sources, and "Cold Storage and Hardware Wallets" (`cold-storage-and-hardware-wallets`) with 10 River-derived sections. These are not "short attributed references" — they are substantial extractions. Either the provenance table overstates what was taken, or LICENSES.md understates it. This is a material license-risk disclosure gap.

6. **SAFETY_CASE §3 evidence count mismatch**: SAFETY_CASE says "22 Kotlin + 44 Python" but README says "22/22 JVM unit tests and 41/41 Python harness tests." Same issue as #1, but in the reverse direction — SAFETY_CASE is correct (per commit message), README is stale.

## Minor

7. **TestCorpusVendorNeutrality vendor regex misses common vendor names**: The `VENDOR` regex includes `trezor|ledger|bitbox|blockstream|jade|seedsigner|krux|liana|sparrow|coldcard|casa|unchained|river|swan|strike` but omits several vendors that appear in the corpus provenance table: **BitBox** (covered by `bitbox`), **Shift Crypto** (the company behind BitBox, not covered), **FTC** (not a vendor, correctly excluded), **bitcoin.org** (not a vendor, correctly excluded), and **Mastering Bitcoin / bitcoinbook** (not a vendor, correctly excluded). More notably, it omits **Foundation Devices** (Passport), **Coinkite** (Coldcard's company, though `coldcard` is covered), **Specter**, **BlueWallet**, **Electrum**, and **Nunchuk** — all plausible vendor names in a Bitcoin custody corpus. The regex would fail to catch "Foundation Devices Passport is the best hardware wallet" or "Electrum is the most trusted desktop wallet." This is a false-negative risk for the exact class of sentence the review feared.

8. **TestCorpusVendorNeutrality superlative regex is narrow**: The `SUPERLATIVE` regex only matches `the best|the top|the leading|the most trusted|number one|#1|we recommend`. It misses common ranking language like "the safest", "the most secure", "the easiest", "the gold standard", "industry standard", "best-in-class", "top-rated", "highly recommended", "our pick", "the only choice", etc. A sentence like "Ledger is the safest hardware wallet" would pass the lint despite being an undated vendor ranking. The test would not catch the full class of ranking claims the review feared.

9. **TestCorpusVendorNeutrality `test_dates_present_near_rankings` only checks `the best|the top`**: The third test narrows the superlative check to only `the best|the top`, so even if the `SUPERLATIVE` regex were broadened, this test would not enforce dates for other superlatives. A sentence like "Ledger is the most trusted hardware wallet" (no date) would pass all three tests.

Without the full table, this cannot be fully verified, but the commit message says "50 rows" and the README says "50 entries" — these should be cross-checked against the actual corpus JSON file count. If the corpus has 50 JSON files but the provenance table has fewer rows (or vice versa), that's a discrepancy.

11. **ChatPlaceholderScreen.kt: `isSecret = false` comment is misleading**: In `runAnswer`, the composed context sets `isSecret = false` with the comment "secret questions are refused before reaching here." This is a real UI honesty/safety gap: the UI implies secret detection is "FIRST in every path" (per the class docstring and SAFETY_CASE M3), but the Answer button skips it.

Minor UX inconsistency.

19. **WalkthroughScreen.kt: progress key uses `step.hashCode()`**: `String.hashCode()` is deterministic within a JVM run but not guaranteed stable across JVM versions or Android API levels. If the app is updated and the Android runtime changes its `String.hashCode()` implementation (unlikely but possible), all walkthrough progress would be lost. Using the step string itself (or a stable hash like SHA-256) would be safer. Minor robustness issue.
